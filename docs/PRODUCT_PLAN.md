# Patchbay — IM 中继与 Bot 网关产品规划（详细版）

> **Patchbay** 为本项目对外名称；**官方主仓**：[https://github.com/yclenove/patchbay](https://github.com/yclenove/patchbay)  
> **Go 二进制名** `patchbay`（系统上若冲突可选用 `patchbayd`）。  
> 定位：在 **自托管、轻运维、强场景** 前提下，为 Telegram（及扩展 Discord）社群与小型团队提供 **消息中继 + 管理控制台 + 可扩展 Bot 能力**，不与「全家桶多协议桥」「企业客服 SaaS」正面拼功能广度。  
> **已定技术栈：全 Go（中继 + 管理 API + Bot）+ Vue 3（控制台）+ PostgreSQL。** 历史仓库 `telegram-relay`、`telegram-relay-admin` 可作为实现参考或逐步迁移进本主仓；`telegram-query-bot`、`im-bot-hub`（Java）不继续作为目标架构。

## 2. 背景与机会

### 2.1 市场空隙

- **Matterbridge** 等：协议多，但配置与学习成本高，「生产可观测、防事故默认值」往往靠用户经验。  
- **Matrix + Mautrix**：能力强，运维与资源占用对「小群/VPS」偏重。  
- **Chatwoot**：强在坐席与多渠道客服，不是「群与频道之间同步广播」心智。  
- **机会**：用 **更窄的协议面 + 更硬的默认安全策略 + 更低的上手路径** 服务「只要 TG/Discord 稳」的群体。

### 2.2 产品原则（写进 README 的价值观）

1. **默认安全**：最小权限 Token、敏感配置不落日志、可选消息脱敏。
2. **默认防事故**：新装默认建议 **单向**；双向必须显式确认与环路检测。
3. **可观测优先**：同步状态、失败队列、速率限制指标在控制台可见。
4. **扩展不绑架**：核心中继不依赖某一云厂商；插件/Webhook 可选。
5. **诚实边界**：对外列出 **支持/实验性/明确不支持** 的平台与能力。

## 5. 产品形态与模块划分

### 5.1 三模块架构（逻辑分层；实现上推荐单体或双二进制）

```
┌─────────────────────────────────────────────────────────┐
│  Console（Web）  Vue 3 + TS + Vite                       │  静态资源 + 调 Go REST API
├─────────────────────────────────────────────────────────┤
│  Go 服务（同一进程或 patchbay + worker 子命令）            │
│    · Core（中继） 路由 / 去重 / 限速 / 环路检测             │
│    · HTTP API     配置 CRUD、鉴权、健康与指标             │
│    · Bot Gateway  TG/Discord Bot、命令、Webhook 入站      │  与 Core 同库、同配置源
├─────────────────────────────────────────────────────────┤
│  PostgreSQL      配置、路由表、审计、可选出站队列表         │
└─────────────────────────────────────────────────────────┘
```

### 5.2 统一事件模型（跨模块契约）

- 所有进出消息归一为 **Envelope**（建议字段）：`event_id`、`source`（platform/channel/thread）、`direction`、`author`（id/ display）、`text`、`attachments[]`、`reply_to`、`edited/deleted`、`raw_ref`（可选，默认关闭持久化）。  
- **出站 Webhook**：`POST /user-hook` JSON，便于接 AI、告警、存档。  
- **入站**（后期）：经鉴权的 HTTP API 触发「向指定目标发送消息」。

## 7. 非功能需求（NFR）


| 类别  | 要求                                                                                        |
| --- | ----------------------------------------------------------------------------------------- |
| 可用性 | 单实例 small VPS（如 1C1G）在 **5 个并发路由、低频消息** 下 CPU 可接受；文档写清上限。                                 |
| 可靠性 | 进程崩溃自动拉起（systemd/Docker restart）；**出站失败重试**落库（Postgres）或明确仅内存重试的范围；备份与恢复文档（`pg_dump` 周期）。 |
| 安全  | HTTPS 控制台；CSRF；会话超时；RBAC（管理员/只读）。                                                         |
| 隐私  | 默认 **不存消息全文** 或短 TTL；可配置「仅元数据」模式。                                                         |
| 国际化 | 控制台中/英；错误码英文化便于搜 issue。                                                                   |

## 8. 技术栈与实现约定（已定：全 Go + Vue + Postgres）

### 8.1 总览


| 层次    | 选型                                   | 说明                                                                                                    |
| ----- | ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 运行时   | **Go 1.22+**（版本号随 LTS 调整）            | 中继、REST API、Bot 长轮询/Webhook **同一仓库**；默认 **单二进制** `patchbay`（可用子命令 `serve` / `migrate`；可选独立 `worker`）。 |
| 前端    | **Vue 3 + TypeScript + Vite**        | 控制台；调用同源或反向代理后的 **REST + JSON**。                                                                      |
| 数据库   | **PostgreSQL 15+**                   | 配置、路由、规则、审计日志、可选 **出站任务/死信表**；不用 SQLite 作为主库，避免与「生产默认可备份」分叉。                                          |
| 部署    | **Docker Compose**                   | 服务：`patchbay`（Go）+ `postgres` + 可选 `nginx`（托管前端 `dist`）；镜像多阶段构建。                                      |
| IM 协议 | **Telegram Bot API、Discord Bot API** | 仅官方 Bot；不引入 JVM/Node 作为核心运行时。                                                                         |


### 8.2 Go 工程结构（建议，可随首仓微调）

- `cmd/patchbay`：入口（二进制名 `patchbay`）。  
- `internal/relay`（或 `internal/core`）：路由、去重、环路检测、限流（包名可用领域词 `relay`，不必与产品名相同）。  
- `internal/bot`：TG/Discord adapter，统一 Envelope。  
- `internal/api`：HTTP 路由、中间件、OpenAPI 可选。  
- `internal/store`：`database/sql` 或 **sqlc** / **pgx** + 迁移（**golang-migrate** 或 **goose**）。  
- HTTP 框架任选成熟轻量库（如 **chi**、echo、fiber），**不强制** gRPC。  
- 日志：**slog** 或 zap；指标：`/metrics`（Prometheus）。

### 8.3 队列与突发

- **默认**：内存 channel 消费 + **失败持久化到 Postgres**（重试次数、下次重试时间），避免 Day1 依赖 Redis。  
- **可选演进**：高并发或多 worker 横向扩展时，再 ADR 引入 **Redis** 或消息中间件。

### 8.4 配置与安全

- **密钥**：仅环境变量或 Docker secrets；不入库明文 Bot Token（若存表则加密列或 KMS 后置）。  
- **配置即代码**：导出/导入路由与规则为 YAML/JSON，与 UI 双向同步（后期）。

### 8.5 测试与仓库

- 契约测试覆盖 **Envelope** 与环路场景；集成测试可用 **testcontainers** 起 Postgres（可选）。  
- **推荐 monorepo**：`/` 下 `cmd/`、`internal/`、`web/`（Vue）；降低 Go 与前端版本漂移。

### 8.6 与历史代码关系

- 现有 **Go relay** 逻辑可迁移或对照实现；**Vue admin** 可作为 UI 起点重写页面。  
- **Java bot 仓**不作为目标栈；新功能一律不进 JVM。  
- **上游参考** [telegram-relay](https://github.com/yclenove/telegram-relay) 的 `main` 已推进：含 **接入凭证（ingest credentials）**、**规则预设**、部署文档与打包脚本等；对照 API/数据模型时以该仓 **最新 `origin/main`** 为准，勿再以未同步的旧目录为真相源。

## 9. 商业化与 GTM

### 9.1 定价思路（从轻到重）

1. **核心开源免费**（自托管），建立信任与 issue 反馈。
2. **Pro**：多实例、OIDC、高级审计、商业许可（可选闭源插件包）。

4. **托管**：按消息量或路由数阶梯订阅（晚于前 3 条验证）。

### 9.2 获客与内容

- **垂直内容**：「TG 频道同步到 Discord 不循环」「开源项目多群公告一篇搞定」。

## 13. 附录：对外「不支持 / 实验性」清单（初稿）

**明确不支持（v1.x）**

- 个人微信机器人、非官方 WhatsApp 个人号协议。  
- 替代企业 IM 的 SSO/审批流全家桶。  
- 保证 100% 消息语义一致（各平台能力差异说明）。

**实验性**

- MCP 只读工具。  
- 入站 Webhook 发送消息（强鉴权下小流量）。
